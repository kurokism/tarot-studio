# タロット占い・演出アプリ 基本設計書

## 1. 文書概要

### 1.1 目的

本書は、要件定義書に基づき、タロット占い・演出アプリのシステム全体の構成および基本的な設計方針を定義する。

### 1.2 対象範囲

本書では、以下の内容を定義する。

- システム全体の構成
- 機能構成および機能間の関係
- アプリケーション構成
- データの基本的な構成
- データ保存の基本方針
- 占い処理の基本方針
- 画面構成の基本方針
- 演出・配信表示の基本方針
- 外部連携
- 拡張性・保守性に関する基本方針
- 技術構成に関する基本方針

---

## 2. 基本設計方針

### 2.1 基本方針

本アプリは、実物のタロットカードを使用した占い結果を入力し、配信画面上で再現・演出できる構成とする。

また、各機能およびデータの責務を分離し、機能追加や変更による影響範囲を抑えられる構成とする。

### 2.2 設計上の方針

以下の方針で設計する。

- カード、デッキ、スプレッド等のデータを独立して管理する
- 占い結果と表示・演出を分離する
- 操作用の画面と配信表示用の画面を分離する
- ユーザーが登録したデータをアプリケーション本体から分離して管理する
- 特定のデッキやスプレッドに依存しない汎用的な構成とする
- 将来的な機能追加を考慮した構成とする

### 2.3 MVPにおける設計方針

MVPでは、実物のタロットカードを使用した手動占いを中心とする。

ランダム占い等のMVP対象外の機能についても、既存の構成を大きく変更せず追加できるようにする。

## 3. システム全体構成

### 3.1 システム構成

本アプリは、以下の機能群から構成する。

- 設定
- カード管理
- デッキ管理
- スプレッド管理
- 手動占い
- ランダム占い
- 演出
- OBS表示
- 占い履歴

各機能は独立した責務を持ち、必要に応じて他の機能が管理するデータを利用する。

### 3.2 機能間の関係

カード、デッキ、スプレッドは占いに必要な基礎データとして管理する。

占いによって得られた結果は、演出・配信表示および占い履歴で利用する。

```text
カード管理 ─────┐
                │
デッキ管理 ─────┤
                ├──→ 占い ──→ 占い結果
スプレッド管理 ─┘              │
                               ├──→ 演出
                               ├──→ OBS表示
                               └──→ 占い履歴

設定
```

## 4. 機能構成

### 4.1 機能一覧

本アプリは、要件定義書で定義した以下の機能から構成する。

| ID | 機能名 | 概要 |
|---|---|---|
| F00 | 設定 | アプリの設定およびヘルプを管理する |
| F01 | カード管理 | カード情報を登録・編集・削除する |
| F02 | デッキ管理 | デッキを作成し、使用するカードを管理する |
| F03 | スプレッド管理 | スプレッドおよびカード配置位置を管理する |
| F04 | 手動占い | 実物のカードを使用した占い結果を入力する |
| F05 | ランダム占い | アプリ内でカードをランダムに選択して占う |
| F06 | 演出 | 占い結果の表示およびカード演出を行う |
| F07 | OBS表示 | 配信向けの占い結果を表示する |
| F08 | 占い履歴 | 過去の占い結果を保存・表示する |

### 4.2 各機能の責務

各機能は以下の責務を持つ。

#### F00 設定

アプリ全体に関わる設定を管理する。

#### F01 カード管理

カードの基本情報および画像等を管理する。

#### F02 デッキ管理

使用するカードの組み合わせをデッキとして管理する。

#### F03 スプレッド管理

占いで使用するカードの配置位置や位置ごとの意味を管理する。

#### F04 手動占い

実物のカードを使用した占い結果をアプリへ入力し、結果を確定する。

#### F05 ランダム占い

デッキおよびスプレッドをもとに、アプリ内で占い結果を生成する。

MVPでは実装対象外とし、将来機能として扱う。

#### F06 演出

確定した占い結果をもとに、配信表示画面上のカードやスプレッド等の演出を制御する。

#### F07 OBS表示

視聴者向けの配信表示画面を提供する。

#### F08 占い履歴

確定した占い結果を保存し、過去の占い結果を確認できるようにする。

## 5. アプリケーション構成

### 5.1 構成方針

アプリケーションは、画面表示、アプリケーション処理、データ管理、データ保存等の責務を分離した構成とする。

### 5.2 基本構成

アプリケーションは、以下の構成を基本とする。

```text
UI
 ↓
Application
 ↓
Domain / Data
 ↓
Persistence
```

各構成要素の役割は以下のとおりとする。

| 構成要素 | 役割 |
|---|---|
| UI | 画面表示、ユーザー操作の受付 |
| Application | ユーザー操作に応じた処理、各機能の連携 |
| Domain / Data | アプリケーションで扱うデータおよび関連する処理 |
| Persistence | データの保存・読み込み |

### 5.3 UI

UIでは、ユーザーが操作する操作画面と、視聴者向けの配信表示画面を提供する。

UIから直接データ保存処理を行わず、Applicationを介して処理を実行する。

### 5.4 Application

Applicationでは、UIから受け取った操作をもとに各機能の処理を実行し、機能間の連携を行う。

### 5.5 Domain / Data

Domain / Dataでは、アプリケーションで扱う主要なデータおよび、それらに関係する処理を管理する。

主な対象は以下とする。

- Card
- Deck
- Spread
- ReadingResult
- Settings

具体的なデータ構造については、data-design.mdで定義する。

### 5.6 Persistence

Persistenceでは、ユーザーデータおよびアプリケーションの設定等を永続化する。

具体的な保存方式については、data-design.mdおよびarchitecture.mdで定義する。

## 6. データ構成

### 6.1 構成方針

アプリケーションで扱う主要なデータを独立して管理し、各データの責務を明確にする。

カード、デッキ、スプレッド等のマスターデータと、実際の占いによって確定した占い結果を分離して管理する。

### 6.2 主要データ

本アプリでは、以下のデータを主要なデータとして扱う。

| データ | 概要 |
|---|---|
| Card | タロットカードの情報 |
| Deck | 使用するカードのセット |
| Spread | カードの配置方法 |
| ReadingResult | 1回の占いで得られた結果 |
| Settings | アプリケーションの設定 |

### 6.3 データ間の関係

主要データ間の基本的な関係は以下とする。

```text
Card
  ↑
  │
Deck ──────┐
           ├──→ ReadingResult
Spread ────┘
```

Deckは使用するCardの集合を管理する。

Spreadは占いにおけるカードの枚数や配置を管理する。

ReadingResultは、選択したDeckおよびSpreadをもとに、実際の占いで使用したカードとその向きを記録する。

Settingsは、他の主要データとは独立して管理する。

### 6.4 占い結果の保持

占い結果は、占いを実施した時点の結果を保持できる構成とする。

カード、デッキ、スプレッド等のマスターデータが後から変更された場合でも、過去の占い履歴に影響しないようにする。

具体的な保持方法については、data-design.mdで定義する。

### 6.5 ユーザーデータ

ユーザーが登録・変更するデータおよびカード画像等のファイルは、アプリケーション本体とは分離して管理する。

アプリケーション本体の更新によってユーザーデータが失われない構成とする。

具体的な保存形式、保存場所、ファイル構成については、data-design.mdおよびarchitecture.mdで定義する。

## 7. データ保存の基本方針

### 7.1 基本方針

ユーザーが登録・変更したデータおよび占い履歴等は、アプリケーション終了後も保持される構成とする。

また、アプリケーションの更新や再起動によって、ユーザーデータが失われないようにする。

### 7.2 保存対象

以下のデータを永続的に保存する。

- カード情報
- デッキ情報
- スプレッド情報
- 占い履歴
- 設定
- ユーザーが登録したカード画像等のファイル

### 7.3 データの独立性

ユーザーデータはアプリケーション本体とは分離して管理する。

アプリケーション本体の更新によって、ユーザーデータが意図せず失われない構成とする。

### 7.4 異常終了時のデータ保持

アプリケーションが異常終了した場合でも、既に保存済みのデータが可能な限り保持される構成とする。

## 8. 占い処理の基本方針

### 8.1 基本方針

占い処理は、選択したデッキおよびスプレッドをもとに、各配置位置に対するカードとその向きを確定する。

手動占いで確定した結果およびランダム占いで生成した結果は、共通の占い結果として扱う。

### 8.2 手動占い

MVPでは、実物のタロットカードを使用した手動占いを基本とする。

基本的な処理の流れは以下とする。

```text
デッキ選択
    ↓
スプレッド選択
    ↓
実物のカードを引く
    ↓
引いたカードを入力
    ↓
カードの向きを入力
    ↓
結果表示
    ↓
占い結果を確定
```

アプリは実物のカードを認識するのではなく、ユーザーが引いたカードの情報を入力する方式とする。

確定した占い結果は、配信表示および履歴保存に利用する。

### 8.3 ランダム占い

ランダム占いでは、選択したデッキに含まれるカードから使用するカードをランダムに選択し、各カードの向きをランダムに決定する。

ランダム占いはMVPでは実装せず、将来機能として扱う。

## 9. 画面構成の基本方針

### 9.1 構成方針

本アプリでは、ユーザーが操作する操作画面と、配信時に視聴者へ表示する配信表示画面を分離する。

操作画面では、各種データの管理および占いの入力・実行を行う。

配信表示画面では、確定した占い結果の表示および演出を行う。

### 9.2 操作画面

操作画面では、以下の機能を提供する。

- カード管理
- デッキ管理
- スプレッド管理
- 手動占い
- ランダム占い
- 占い履歴
- 設定

操作画面は、機能を切り替えて利用できる構成とする。

### 9.3 占い画面

占い画面では、選択したデッキおよびスプレッドをもとに占いを行う。

手動占いでは、ユーザーが実物のカードを引いた後、各配置位置に対応するカードと向きを入力する。

入力完了後、結果表示操作によって占い結果を確定し、配信表示画面へ反映する。

### 9.4 配信表示画面

配信表示画面は、確定した占い結果を視聴者へ表示することを目的とした画面とする。

主な表示対象は以下とする。

- カード
- スプレッド
- カードの向き
- 占い結果に関連する情報
- 演出

配信表示画面は、操作画面とは独立して表示できる構成とする。

### 9.5 画面間の関係

操作画面と配信表示画面の基本的な関係は以下とする。

```text
操作画面
    │
    ├── カード・デッキ・スプレッド管理
    │
    └── 占い
          ↓
      占い結果
          ↓
    配信表示画面
          ↓
        演出
          ↓
         OBS
```

操作画面から行った操作によって、配信表示画面の内容を更新する。

## 10. 演出・配信表示の基本方針

### 10.1 基本方針

演出は、確定した占い結果を視聴者に分かりやすく伝えるため、配信表示画面上で行う。

操作画面では演出を行わず、ユーザーが占いの操作や結果の確認を行いやすい構成とする。

### 10.2 演出対象

演出の対象は、配信表示画面に表示される占い結果とする。

主な演出対象は以下とする。

- カードの表示
- カードの配置
- カードの向き
- スプレッドの表示
- 占い結果に関連する情報

### 10.3 演出の基本的な流れ

結果表示操作を起点として、配信表示画面へ占い結果を反映し、演出を行う。

```text
結果表示操作
    ↓
占い結果を確定
    ↓
配信表示画面へ反映
    ↓
演出
```

演出完了後も、確定した占い結果を配信表示画面に表示する。

## 11. 外部連携

### 11.1 基本方針

本アプリは、基本的に単体で動作する構成とする。

外部のソフトウェアやサービスを利用する場合は、アプリケーション本体との責務を分離し、必要な範囲で連携する。

### 11.2 配信ソフトウェア

配信時には、OBS等の配信ソフトウェアからアプリの配信表示画面をキャプチャして利用する。

```text
アプリ
  │
  └── 配信表示画面
          ↓
        OBS
          ↓
        配信
```

操作画面は配信画面とは分離し、ユーザーが操作している内容を視聴者へ直接表示しない構成とする。

---

## 12. 拡張性・保守性の基本方針

### 12.1 基本方針

将来的な機能追加や既存機能の変更を考慮し、各機能および各データの責務を分離した構成とする。

特定の機能やデータの変更が、他の機能へ過度に影響しない構成を基本とする。

### 12.2 機能の拡張

MVPでは実装しない機能についても、既存の構成を大きく変更せず追加できる構成とする。

### 12.3 データの拡張

カード、デッキ、スプレッド等のデータについて、将来的に新しい種類や項目を追加できる構成とする。

また、ユーザーが独自のカードやスプレッドを登録できることを前提とし、特定のデータのみを対象とした構成としない。

### 12.4 保守性

各機能の責務を明確にし、機能ごとの変更や修正を行いやすい構成とする。

また、画面、アプリケーション処理、データ管理、データ保存等の責務を分離し、変更による影響範囲を抑える。
